## 1. Architecture (MVP §9)

The MVP is built as a **modular monolith with event-driven AI/MCP services**. This avoids premature microservice complexity while keeping clean domain boundaries. Each domain module owns its tables and talks to other modules only through its public interface or domain events, so any module can later be extracted into its own service without a redesign.

## 3. Multi-Language & Localization Strategy (EN/FA first) (MVP §15 Localization readiness)

The MVP launches with English (EN) and Persian (FA). New languages must not require code changes.

### 3.1 UI dictionary (static platform text)
- **Storage:** version-controlled JSON files in `shared/i18n/locales/` (`en.json`, `fa.json`), published to the CDN (e.g. `cdn.carpal.app/i18n/v1/fa.json`). **Not stored in the database.**
- **Structure:** nested keys, e.g. `{"errors": {"vehicle_not_found": "Vehicle not found"}}`.
- **Clients:** `react-i18next` (web/PWA) and `i18next` (React Native). Each app **bundles a fallback copy** for first launch and offline use, and fetches newer versions from the CDN, then caches them.
- **CI rule:** the build fails if any key in `en.json` is missing from `fa.json` (or any other enabled locale).

### 3.2 RTL support
- Persian requires right-to-left layout. Web uses Tailwind **logical utilities** (`ms-*`, `me-*`, `ps-*`, `pe-*`, `start-*`, `end-*`) and `dir="rtl"`; React Native uses `I18nManager`.
- Directional icons (arrows, chevrons, progress) are flipped by rule; non-directional icons (logos, media controls) are not.

### 3.3 Dynamic data translation (entity data)
- Translatable fields (provider descriptions, taxonomy labels, inventory names, etc.) use PostgreSQL **JSONB** columns, e.g. `inventory_items.name_translations = {"en": "Brake Pad", "fa": "لنت ترمز"}`.
- The API reads `Accept-Language` and returns the requested language, with **English as the fallback**.
- **GIN indexes** on JSONB translation columns. Persian analyzers in the search index.

### 3.4 Regional formats (MVP §15)
- Local currency (stored as amount + ISO currency code).
- Local date/time formats, including the **Jalali (Solar Hijri) calendar** for FA, with all timestamps stored in UTC.
- Persian/Arabic-Indic digits for display, Latin digits for storage.
- Local phone (E.164 storage) and address formats.
- Regional vehicle taxonomies (region-specific brands/models are flagged in taxonomy).

## 5. Cross-Cutting Engineering Rules

These apply to every work package.

1. **Tenancy and isolation (MVP §5.1, §14):** every tenant-owned row carries an owner (user or organization). PostgreSQL RLS + application guards enforce that user A cannot reach organization B's data. Vendor private inventory and fleet data are isolated per organization.
2. **Consent (MVP §14):** consent is a recorded entity checked before sharing vehicle data/service history with a provider, publishing photos/showcases, AI personalization, review invitations, and fleet manager visibility of driver data.
3. **Domain events (MVP §9.6):** modules publish events through the transactional outbox. Required events: `user.registered`, `vehicle.created`, `vehicle.updated`, `provider.profile.published`, `vendor.inventory.imported`, `inventory.updated`, `appointment.requested`, `appointment.confirmed`, `appointment.completed`, `review.created`, `review.published`, `review.reported`, `portfolio.published`, `service_record.created`, `qna.question.created`, `inquiry.sent`, `ai.insight.generated`, `moderation.action.taken`.
4. **Event consumers (MVP §9.6):** search indexer, AI insight generator, notification service, analytics pipeline, trust scoring pipeline, skill heatmap pipeline, fraud detection pipeline, MCP audit logger.
5. **AI goes through MCP (MVP Rule 10):** no AI feature reads domain data directly. All AI context and actions go through the MCP gateway (WP17).
6. **AI output is stored as an AI Insight (MVP §5.13):** AI-generated content is never silently mixed with source data.
7. **Graceful degradation (MVP §15):** if AI is unavailable, manual search, profiles, and appointments still work.
8. **Audit (MVP §15, §13):** moderation actions, admin actions, plan changes, consent changes, and all AI/MCP actions are written to an append-only audit log.
9. **Security (MVP §15):** TLS everywhere, encryption at rest, RBAC, secure file upload with malware scanning, rate limiting, secrets in a managed secret store, MCP token scoping.
10. **Accessibility (MVP §15):** readable contrast, screen reader support, accessible forms, simple language, large tap targets on mobile.
11. **Phase 2/3 hooks (MVP §2):** data structures and MCP hooks are created now for future capabilities (see §9.3 of this plan), but those features are not built.

### WP8 — Discovery, Search & Matching
- **Scope:** Discovery/Search module (MVP Module E, §12). Search targets: providers, vendors, parts, vehicle-specific expertise, symptoms/issues, service categories, locations, posts/showcases, Q&A. Inputs: free text, vehicle context, location, category, urgency, availability, rating, badges, price indicator, provider/vendor type. All provider filters and vendor filters listed in Module E. **Text search** (typo tolerance, synonyms, partial matching, category mapping), **geo search** (radius, service area, distance sort), **semantic search** (embeddings via pgvector, produced by WP17/WP18), **contextual search** (selected vehicle auto-filters brand/model/series/engine/year). Search indexer worker building projections for providers, vendors, inventory items, showcases, Q&A, service categories, symptoms.
- **Matching engine:** combines explicit fit, evidence fit, category-specific rating quality, recency, availability, location, trust signals, and user preference (favorites, fleet-approved lists). Ranking factors for providers, vendors, and inventory exactly as MVP §12, with weights and time decay from [54.Scoring Protocol](54.Scoring%20Protocol.md).
- **Match explanations:** every recommendation stores **structured reasons** (capability evidence, rating evidence, location, availability, urgency fit, user preference). AI renders the human-readable text (WP18); a template-based text is the fallback when AI is unavailable.
- **Rule:** paid/featured placement is shown separately and never changes organic trust ranking (MVP §7.1.7, Rule 2).
- **Search results show:** name, distance, rating, relevant badge, match explanation, availability, portfolio thumbnail, price indicator, verified status, response time.
- **Acceptance:** search latency target agreed in WP0 (§15 "respond quickly under normal load"); results never leak private inventory; explanations exist for 100% of ranked results.
- **Tests:** relevance test set (EN + FA), geo correctness, ranking determinism, tenant isolation in the index, performance tests.
- **Depends on:** WP4–WP7, WP9 (trust signals), WP10 (availability). **Owner:** Backend engineers, Search engineer (part-time). **Stage:** 3. **Priority:** Must.

## 14. Critical Success Factors

1. **Strict API contracts:** OpenAPI generated from the backend, TypeScript clients generated into `shared/api-contracts`. A breaking API change fails the web, PWA, and mobile builds.
2. **UI dictionary CI:** `en.json` and `fa.json` are version-controlled; CI fails when a translation key is missing.
3. **JSONB indexing:** GIN indexes on JSONB translation columns; Persian analyzers in the search index.
4. **RTL-first design:** the design system is built with RTL from day one. Margins, paddings, and directional icons are logically flipped, not just mirrored.
5. **Module boundaries:** modules never read another module's tables directly; they use public interfaces or events. This keeps later service extraction cheap.
6. **AI only through MCP:** no shortcut data access for AI features, so consent, redaction, and audit stay consistent.

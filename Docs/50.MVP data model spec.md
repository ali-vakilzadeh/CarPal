# 1. Data Model Goals

The MVP data model must support every Must-Have item in Plan §8.1:

- four role families, multi-role users and organizations
- vehicle profiles, service history, issues and maintenance reminders
- provider capability portfolios built on evidence
- vendor inventory, fitment, trade pricing and stock inquiries
- reviews, the trust graph, trust signals and rule-based badges
- search, intelligent matching and stored match explanations
- appointments, provider calendar and pre-visit reports
- fleet management, approvals, costs and reports
- lightweight community features
- media with consent, redaction and malware scanning
- notifications across in-app, email and push
- admin, moderation, feature flags and audit
- analytics for all MVP §16 metrics
- AI/MCP context, insights, approvals, evaluation and audit
- EN/FA multi-language data and regional formats
- GDPR-style consent and data subject requests

It must also hold the extension points for Phase 2/3 (Plan §8.4) without building those features.

# 2. Architecture Alignment (Plan §1, §2, §5)

| Concern | Rule |
|---|---|
| Ownership | Every entity belongs to exactly one backend module (Plan §1.2) or to the AI/MCP platform. The owning module is the only code that writes it. |
| Cross-module references | Stored as IDs (`xref` in 52) with **no cross-module foreign keys**. Validated through the owning module's interface or events (Plan §14.5). This keeps later service extraction cheap. |
| Events | State changes publish domain events through a transactional outbox (§20, Plan §5.3). |
| AI | AI reads and writes only through MCP. AI output is stored as `AiInsight`, never mixed silently into source data (Plan §5.5–5.6). |
| Tenancy | PostgreSQL Row-Level Security on every org-private and user-private table (Plan §5.1). |

Data stores (Plan §2):

| Store | Holds |
|---|---|
| PostgreSQL (primary) | All system-of-record entities in this document |
| pgvector (in PostgreSQL) | `Embedding` vectors for semantic search and AI similarity |
| PostgreSQL (analytics database) | `AnalyticsEvent` and aggregates |
| Elasticsearch | Search projections (§11), rebuilt from events |
| Redis | Sessions, cached profile summaries, availability slots, feature flags, job queues |
| Object storage + CDN | Media files, documents, exports, UI dictionary |
| NATS JetStream | Domain event streams relayed from the outbox |

# 3. Conventions

Full rules are in 52 §1–§2. Summary:

- **IDs:** UUID (UUIDv7 recommended).
- **Common fields:** `id`, `created_at`, `updated_at`, `created_by`, `updated_by`, `status`, `version`.
- **Soft delete:** `deleted_at`, `deletion_reason`; hard delete and anonymization follow `DataRetentionPolicy` and `DataSubjectRequest`.
- **Tenancy classes:**

| Class | Meaning | Examples |
|---|---|---|
| public | Readable by anyone once published or approved | Published profiles, reviews, portfolio items, public inventory |
| user-private | Owned by one user | Personal vehicles, consents, preferences, triage sessions |
| org-private | Owned by one organization | Inventory internals, fleet vehicles and costs, provider customer notes, provider analytics |
| platform-internal | Staff and system only | Moderation cases, audit logs, MCP logs, feature flags |

- **Multi-language (Plan §3.3):** platform-curated and business-authored catalog text uses `<field>_translations` JSONB columns with GIN indexes. Reads fall back from the requested locale to `en`. User-generated content stores `content_locale` instead. UI text, notification templates, plan names and badge titles live in the UI dictionary, not the database.
- **Regional formats (Plan §3.4):** UTC timestamps, money as amount + ISO 4217 currency, E.164 phones, ISO country codes, Latin digits in storage, kilometres for distance and mileage. Jalali calendar and Persian digits are display concerns driven by `UserPreference`.

# 5. Identity & Access — `identity` (WP2)

**UserAccount** — a human login. Key fields: name, display name, email, phone, locale, timezone, verification timestamps, MFA flag, status. Has many role memberships, consents, preferences. May own personal vehicles and author reviews, questions and comments.

**AuthenticationMethod** — email/password, phone OTP, OIDC social login, TOTP MFA. Credentials are references to hashes or secrets, never plain text. Sessions live in Redis, not in the database.

**UserPreference** — one per user. Holds the MVP §5.1 role, privacy, notification-mode and AI personalization preferences, plus regional display settings (calendar system, digit style, distance unit, currency).

**RoleMembership** — links a user to an organization and role. One user can be an individual owner, a shop employee and a fleet manager at once (MVP §5.1). Roles cover individual, fleet (owner, manager, maintenance coordinator, driver, viewer), provider (owner, manager, staff), vendor (owner, staff) and platform staff (admin, moderator, support). Permissions follow the WP0 permission matrix.

**ConsentRecord** — every consent area in MVP §14 and every MCP consent rule in MVP §8.5. A consent can be scoped to one record (e.g. one vehicle) and granted to one party (e.g. one provider). Withdrawal is immediate.

**DataSubjectRequest** — export, deletion, rectification and consent withdrawal requests (MVP §14), with deadlines and outcomes.

**OnboardingProgress** — progress through the individual, fleet, provider and vendor onboarding flows (MVP Module A). Admins can reset it.

# 6. Organizations & Profiles — `organization` (WP3, WP6, WP7)

**Organization** — a provider, vendor, fleet or hybrid provider+vendor business. Holds names, contacts, translated description, slug, a cached trust score, and a merge pointer for resolved duplicates. Its plan comes from its `Subscription`. Has one provider, vendor or fleet profile depending on type.

**OrganizationLocation** — address, geo coordinates, timezone, service radius, hours, access instructions, primary contact. Location verification feeds completeness and the Verified Business badge.

**OrganizationVerification** — one record per verification check (business identity, address, phone, email, location) with admin review (MVP §13).

## 6.1 Provider capability portfolio (MVP §3.3, §5.5, Module C)

**ProviderProfile** — provider type, translated description, years in business, languages, amenities, service modes (in-shop, mobile, pickup/drop-off), contact channels, price tier, warranty policy, response-time target and measured response time, completeness, activity status, publication status.

**ProviderCertification** — certifications with issuer, scope and document. Only verified certifications count as evidence.

**ProviderServiceCategory** — the service catalog: service systems and tasks the provider offers, with experience level, price indicator and typical duration.

**ProviderVehicleCoverage** — supported brands, models, series, engine and fuel types. Unlimited rows.

**ProviderCapability** — the capability matrix (brand / model / series / system / task / experience level). Each row records its source (self-declared, AI-suggested, job evidence, review evidence, certification, admin-verified), a computed confidence level and score ([54 §2](54.Scoring%20Protocol.md)), and whether it is public and badge-eligible.

**ProviderCapabilityEvidence** — links a capability to the evidence behind it (completed appointment, verified review, portfolio item, service record, certification, job log), with base weight and evidence date for freshness. Evidence cannot be altered once counted. Evidence linked by AI mapping counts only after provider approval.

**ProviderJobLog** — jobs the provider logs as evidence. Links to a customer vehicle only with consent.

**ProviderCustomerNote** — simple private notes about customers. Included in the customer's data export.

**PortfolioItem** — a before/after project with vehicle and service tags, customer consent, an AI caption draft (as an insight) and a human-approved caption. Media are attached through `MediaAttachment` with before/after pairing.

Rule: **AI suggests, provider approves, platform verifies.** AI-suggested catalog, coverage and capability rows start as `pending_provider_approval` and never become public before approval and enough evidence.

## 6.2 Vendor profile (MVP §3.4)

**VendorProfile** — vendor type, translated description and policies, delivery options, trade support, default price visibility, response time, catalog quality score ([54 §7](54.Scoring%20Protocol.md)), completeness, publication status.

**VendorCoverage** — supported brands, models and part categories.

# 7. Plans & Entitlements — `billing` (WP3)

**Plan** — Individual Free, Fleet 20/50/100, Fleet Custom, Provider Basic/Pro, Vendor Basic/Pro (MVP §5.12). Plan names come from the UI dictionary.

**Entitlement** — a key/value capability of a plan: max vehicles, fleet users, AI tools, AI fleet suggestions, inventory item limit, bulk import, appointment capacity tools, advanced analytics, fleet reports, approval workflow, featured placement eligibility, export access.

**Subscription** — links a **user or organization** to a plan, with trial dates, manual assignment by admin, overrides and a reserved external billing reference. Every user gets Individual Free automatically. Entitlements are enforced on the server and plan changes are audited.

---

# 8. Taxonomy — `taxonomy` (WP4)

**TaxonomyNode** — one controlled vocabulary for brands, models, series, engine types, fuel types, service systems, service tasks, part categories, symptoms, review tags and amenities (MVP §5.4). Labels are translated (EN and FA required), nodes can be limited to regions, and type-specific attributes include production years for series and a `safety_critical` flag for symptoms. Duplicate nodes are merged with every reference re-pointed.

**TaxonomySynonym** — synonyms, aliases, misspellings, local terms and abbreviations per locale, for search relevance and AI normalization (MVP §7.5C). AI-suggested synonyms need admin approval.

**TaxonomyMapping** — weighted node-to-node mappings: symptom → system, symptom → task, part category → system, task → part category. These power triage, matching and fitment.

---

# 9. Vehicles & Service History — `vehicle` (WP5)

**Vehicle** — owned by a user or a fleet organization. VIN (encrypted, with hash and decode status), plate, nickname, taxonomy references, year, powertrain details, mileage in km, ownership start date, photo, notes, status, completeness. `obd_profile` is reserved for Phase 2.

**VehicleStatusHistory** — status changes over time. Used for fleet downtime estimates.

**VehicleMileageLog** — mileage readings from users, drivers, service records and appointments.

**VehicleDocument** — insurance, registration, warranty, invoice and inspection documents stored as private encrypted media, shared with a provider only by consent.

**VehicleServiceRecord** — a repair or maintenance record from any MVP source (manual, provider-logged, completed appointment, invoice upload; imported file and OBDII event reserved). Holds parts used, cost and breakdown, warranty, mileage, verification status, visibility, and links to the appointment, job log, resolved issue and AI next-service suggestion.

**ServiceRecordEvidence** — invoices, photos, documents and appointment records that support a service record (`obd_code_future` reserved).

**VehicleIssue** — an active or resolved problem, reported by a user, a fleet driver or AI triage. Links to the triage session and AI insight, fleet approval status and the resulting appointment.

**MaintenanceReminder** — reminders from rules, AI suggestions, manual entry or fleet policy, due by date or mileage.

---

# 10. Vendor Inventory — `inventory` (WP7)

**InventoryItem** — vendor catalog item: SKU, translated name and description, normalized name, part numbers, part origin (OEM/aftermarket), condition, category, position, public and trade prices, price-on-request, stock, location, warranty, visibility (public, trade-only, hidden), data quality score, duplicate link, import batch.

**InventoryFitment** — compatible brand, model, series, year range, engine and fuel type, with confidence (confirmed, likely, uncertain) and source. AI suggestions wait for vendor confirmation.

**VendorTradeAccount** — approved trade relationship between a vendor and a provider or fleet. Only approved trade customers see trade-only items and trade prices.

**StockInquiry** and **InquiryMessage** — inquiry and reservation workflow (no checkout), with a minimal vehicle context snapshot shared only by consent. Messages are thread-ready for future live chat.

**InventoryImportBatch** — CSV import job with column mapping, counts and an error report.

Isolation rules (MVP Module D): vendors see only their own inventory; public users see only public prices and stock; competitors cannot access private catalog data; AI never uses one vendor's private data for another.

---

# 11. Discovery & Matching — `discovery` (WP8)

**MatchSession** — one search or recommendation request: requester, source (search, AI triage, fleet workflow, profile recommendation), vehicle and issue context, query, taxonomy filters, location, urgency, locale.

**MatchResult** — one ranked result with match score ([54 §5](54.Scoring%20Protocol.md)), confidence, **structured reasons** (capability evidence, rating evidence, location, availability, urgency fit, user preference, trust signal, recency), rendered explanation (AI or template), and outcome (viewed, selected, appointment). Sponsored results are flagged and never part of organic ranking.

**Search projections** (Elasticsearch) — ProviderSearchDoc, VendorSearchDoc, InventorySearchDoc, CommunitySearchDoc, TaxonomySearchDoc. They are derived from events, indexed per locale, contain only public data, and never contain trade prices.

---

# 12. Reviews & Trust — `trust` (WP9)

The trust graph (MVP §4) connects users, vehicles, providers, vendors, parts, service records, reviews, photos, appointments, capabilities, locations and time through the references in this model. Trust signals are stored and computed from day one.

**Review** — rating, optional "would return", text, author language, context (vehicle, appointment, service record, inquiry, service system/task, location), verified status, trust weight, helpful count, report status, internal AI sentiment and complaint flags.

**ReviewSubRating** — separate dimensions for providers (work quality, communication, timeliness, price accuracy, cleanliness) and vendors (part accuracy, availability accuracy, price fairness, service speed, communication).

**ReviewTag** — review tags from the taxonomy, chosen by the author or suggested by AI and confirmed.

**ReviewResponse** — public response, with AI-assisted flag and draft insight. Never auto-published.

**ReviewRequest** — review invitation after an appointment or service record, with channel, reminders and conversion.

**Dispute** — fake-review disputes, mediation requests, badge challenges, service record disputes and moderation appeals. Outcomes feed trust signals.

**TrustSignal** — every MVP §4 signal (user-generated, provider-generated, platform-verified, AI-derived) plus the composite trust score and admin penalties, optionally per taxonomy category, versioned by scoring rule.

**ProviderBadge** — rule-based, auditable badges from MVP Module C and [54 §4](54.Scoring%20Protocol.md). Each award stores its rule, version and evaluation snapshot with evidence IDs.

---

# 13. Appointments & Calendar — `appointment` (WP10)

**Appointment** — request-to-completion record: requester (user or fleet), provider and location, vehicle, source, match result, issue, triage session, fleet approval, appointment type, service mode, taxonomy context, description, urgency, customer expectations, proposed and confirmed times, estimated duration and completion window, parts note, check-in link, delay notice, cost estimate, consent, status, cancellation. `payment_reference_future` is reserved. Allowed status transitions are listed in 52 §12.

**AppointmentTimeWindow** — preferred time windows chosen by the requester.

**AppointmentStatusHistory** — immutable status changes.

**AppointmentParticipant** — assigned staff, fleet managers, coordinators and drivers.

**AppointmentNote** — internal or customer-visible notes.

**PreVisitReport** — every MVP Module H item: vehicle identity, mileage, symptoms, user description, AI triage insight and approved summary, likely service categories, relevant history and previous related repairs (consent-gated), known warnings, focus areas, media, customer expectations, urgency, fleet approval status, preferred contact channel. `obd_summary_future` is reserved.

**ProviderAvailabilityRule** and **ProviderTimeOff** — working hours, slot length, appointment types, buffers, concurrency limits and unavailable dates (MVP Module G).

---

# 14. Fleet — `fleet` (WP11)

**FleetProfile** — fleet size, industry, approval workflow switch, cost-approval threshold, preferred-provider mode, reporting currency.

**FleetVehicleAssignment** — driver assignments; one active assignment per vehicle.

**FleetPreferredPartner** — preferred shops and approved vendors, optionally per category.

**FleetApproval** — repair request, provider selection and cost estimate approvals in the MVP Module K workflow (driver reports → AI triage → manager approves → provider selected → appointment → repair → cost logged → vehicle back to active).

**FleetImportBatch** and **FleetExport** — CSV vehicle import and CSV report exports.

Fleet analytics (cost by vehicle, category and month; service frequency; downtime; provider usage; preferred provider performance; most repaired vehicles; common issues) are computed from service records, issues, appointments and `VehicleStatusHistory`, so they need no extra entities.

---

# 15. Community — `community` (WP12)

**Follow** — user follows a provider or vendor, with a notification setting.

**Favorite** — saved favorite providers and vendors; an input to matching preferences.

**Post** — provider or vendor update: showcase, availability, seasonal advice, special offer, educational tip, job completion, community event. Showcases link to a consented portfolio item.

**Comment** — optional comments on posts, showcases, questions and answers.

**Reaction** — helpful and like reactions on reviews, answers, posts, comments and showcases.

**Question** and **Answer** — Q&A tied to a vehicle, symptom or category. Public context uses taxonomy only; the private vehicle link is never shown.

The Discover feed is computed from projections and follows, with no stored entity. There is no full social feed in the MVP (MVP Module J).

---

# 16. Media — `media` (WP13)

**MediaAsset** — every uploaded file: type, MIME, size, checksum, storage and thumbnail keys, privacy level, encryption, malware scan status, EXIF stripping, redaction status (with AI suggestion insight), consent, moderation, status. A file is never served before a clean scan.

**MediaAttachment** — links media to vehicles, issues, portfolio items, posts, reviews, questions, answers, inventory items, appointments, job logs, organizations and users, with a role (gallery, cover, logo, avatar, before, after, evidence, issue photo) and a pair key for before/after grouping.

---

# 17. Notifications — `notification` (WP14)

**Notification** — one event for one recipient: event type (every MVP §5.11 and Module L event), category, priority, UI-dictionary template key and parameters, locale, target reference, read state.

**NotificationDelivery** — one delivery attempt per channel (in-app, email, push, SMS later), with status, provider message ID and errors.

**NotificationPreference** — per channel and category, with frequency (immediate or digest). Critical alerts are always delivered.

**PushDeviceToken** — iOS, Android and web push tokens.

---

# 18. Admin & Moderation — `admin` (WP15)

**ContentReport** — user reports on any content, profile, listing, user or AI output: fake reviews, unsafe advice, counterfeit parts, inaccurate fitment, impersonation, hallucinations and more.

**ModerationCase** — the moderation queue item, opened by reports, AI flags, system rules or admins.

**ModerationAction** — each moderator decision with a mandatory reason, including badge revocation and trust penalties ([54 §9](54.Scoring%20Protocol.md)).

**FeatureFlag** — release, beta, AI-feature and kill-switch flags targeted by role, region, organization, plan or percentage. `ai.automation.kill_switch` overrides all AI features.

**DataRetentionPolicy** — configurable retention and anonymization per entity (MVP §14).

# 19. Analytics, Audit, AI & MCP

## 19.1 Analytics & audit — `analytics` (WP16)

**AuditLog** — append-only record of moderation, admin, plan, consent, badge, trust-score and approval actions.

**AnalyticsEvent** — pseudonymous product events in the analytics database, covering every MVP §16 metric group.

## 19.2 MCP platform — `ai-mcp` (WP17)

**McpClient** — registered internal or future external AI client with scopes, resources, tools, rate limits, geographic restrictions and environment (MVP §5.13, §8.2). Resource and tool definitions are versioned code ([53](53.MCP%20Catalog.md)); prompts are versioned files.

**McpAccessLog** — append-only log of every resource read and tool call: client, principal, tenant, tool version, risk level, context used, consent reference, redactions, policy decision, approval, output insight, model version, result and latency.

**ApprovalRequest** — human approval for AI drafts and sensitive actions (MVP §8.6 "write actions create drafts").

## 19.3 AI orchestration — `ai-mcp` (WP17, WP18)

**AiInsight** — every AI output, with inputs, tool, prompt and model versions, locale, confidence, evidence, safety flags, visibility and approval status. Covers every WP18 feature.

**AiSuggestion** — actionable suggestion derived from an insight, accepted, edited or rejected by a human.

**AiEvaluationRecord** — feedback for the evaluation layer: acceptance, edits, corrections, moderator overrides, hallucination reports, match selection, ratings.

**TriageSession** — the "Help Me" conversation, its classification, urgency and safety outcome, and links to the issue, match session and appointment draft.

**SkillHeatmapEntry** — provider-private strength per brand, model, series, system or task, classified as strong, emerging, weak or opportunity, with trend and local demand.

**Embedding** — pgvector embeddings with tenant scoping for private content.

# 21. Core Relationships

- **Users and organizations:** a user has many role memberships; each links one user to one organization (except `individual` and platform roles). An organization has many locations, members, verifications and one subscription; it has one provider, vendor or fleet profile depending on type.
- **Vehicles:** a vehicle belongs to a user or a fleet organization. It has status history, mileage logs, documents, service records (with evidence), issues, reminders and appointments. A fleet vehicle has at most one active driver assignment.
- **Providers:** a provider has a profile, certifications, service catalog, vehicle coverage, capabilities with evidence, job logs, customer notes, portfolio items, availability rules, time off, badges, trust signals, reviews and skill heatmap entries.
- **Vendors:** a vendor has a profile, coverage, inventory items (with fitment, media and inquiries), trade accounts and import batches.
- **Reviews:** a review is written by a user about an organization, may reference a vehicle, appointment, service record or inquiry, and has sub-ratings, tags, one published response, reactions, reports and disputes.
- **Appointments:** an appointment links requester, provider and vehicle; it may come from a match result, issue or triage session; it has time windows, status history, participants, notes and one pre-visit report; completion creates a service record and a review request.
- **Fleet:** a fleet has a profile, vehicles, assignments, preferred partners, approvals, imports and exports.
- **AI/MCP:** MCP clients read resources and invoke tools; every operation creates an access log; outputs become insights, suggestions and approval requests; feedback becomes evaluation records.

The entity-relationship diagram is in [51.MVP entity Relationship Map.md](51.MVP%20entity%20Relationship%20Map.md).

# 22. Data Integrity Rules

Field-level rules are in 52 §21. The model-level principles are:

1. **Vehicle limits** — active vehicles never exceed the plan's `max_vehicles` (Individual Free 5; Fleet 20/50/100/custom).
2. **Review integrity** — verified statuses require matching evidence; unverified reviews are labeled, weighted lower and excluded from the core score; removed reviews stay for audit.
3. **Capability integrity** — public badges require evidence thresholds; AI-suggested capabilities need provider approval; confidence grows only from evidence; self-declared claims never earn badges.
4. **Vendor isolation** — inventory is tenant-isolated; trade data needs an approved trade account; AI never crosses vendor boundaries.
5. **Fleet privacy** — driver data is limited to fleet operations and needs consent for manager visibility; fleet costs are org-private; providers see only the fleet context needed for the appointment.
6. **Media consent** — public media needs consent where identifiable, a clean malware scan, EXIF stripped, redaction done and moderation approval.
7. **AI separation** — AI never overwrites source data; outputs are insights; human acceptance is recorded before public or operational use; the kill switch stops all AI writes.
8. **No hidden paid ranking** — plans and sponsorship never feed the organic match score.
9. **Auditability** — moderation, admin, plan, consent, badge, trust-score and AI actions are always logged.

# 23. Phase 2/3 Extension Points (Plan §8.3–8.4)

Not built in the MVP:

- OBDII raw telemetry and live ECU streams
- crash detection and SOS events
- payment transactions, refunds, checkout, shipping
- insurance claims
- POS/DMS integrations
- advanced telematics and driver behavior scoring

The model reserves these hooks:

| Future capability | Hook |
|---|---|
| OBDII diagnostics and health scores | `Vehicle.obd_profile`; `VehicleServiceRecord.source_type = obdii_event_future`; `ServiceRecordEvidence.evidence_type = obd_code_future`; `VehicleMileageLog.source = obdii_future`; `PreVisitReport.obd_summary_future`; reserved MCP resource namespace |
| Bluetooth pairing, crash detection, SOS | A future `VehicleDevice` entity linked to `Vehicle` (name reserved) |

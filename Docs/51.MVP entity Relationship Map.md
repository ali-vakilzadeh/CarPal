**concise MVP Entity Relationship Map**

# 1. Cardinality Legend

| Symbol | Meaning |
|---|---|
| `1` | Exactly one |
| `0..1` | Zero or one |
| `*` | Many |
| `1..*` | One or many |
| `ref` | Reference/link to another entity |
| `subject ref` | Polymorphic reference using entity type + entity ID |

---

# 2. High-Level Core ERD

The MVP has five major hubs:

1. **UserAccount**
2. **Organization**
3. **Vehicle**
4. **TaxonomyNode**
5. **Trust/Transaction objects**
   - Review
   - Appointment
   - InventoryItem

## Core relationship spine

```text
UserAccount
  ├── 1..* RoleMembership *── 1 Organization
  ├── 1..* ConsentRecord
  ├── 1..* Notification
  ├── 1..* Review as author
  ├── 1..* Question
  └── 1..* Comment / Reaction

Organization
  ├── 1..* OrganizationLocation
  ├── 1..* RoleMembership
  ├── 0..1 ProviderProfile
  ├── 0..1 VendorProfile
  ├── 0..1 FleetProfile
  ├── 1..* Vehicle if fleet-owned
  ├── 1..* Review as subject
  ├── 1..* Appointment as provider
  └── 1..* Post / PortfolioItem / InventoryItem depending on type

Plan
  └── 1..* Subscription *── 1 Organization

Vehicle
  ├── 1..* VehicleServiceRecord
  ├── 1..* VehicleIssue
  ├── 1..* VehicleDocument
  ├── 1..* MaintenanceReminder
  └── 1..* Appointment

TaxonomyNode
  ├── Parent/child taxonomy hierarchy
  ├── 1..* TaxonomySynonym
  └── referenced by:
      ├── ProviderServiceCategory
      ├── ProviderVehicleCoverage
      ├── ProviderCapability
      ├── InventoryFitment
      ├── ReviewTag
      ├── VehicleIssue symptom/category
      └── Community Question/Answer category
```

# 15. Main Polymorphic References

Some entities use flexible references instead of a single fixed foreign key.

## Common polymorphic patterns

| Entity | Reference Field | Can Refer To |
|---|---|---|
| Vehicle.owner | owner_type + owner_id | UserAccount, Organization |
| Review.context | context_type + context_id | Vehicle, Appointment, VehicleServiceRecord |
| Appointment.requester | requester_type + requester_id | UserAccount, Organization |
| StockInquiry.requester | requester_type + requester_id | UserAccount, Organization |
| AiInsight.subject | subject_type + subject_id | Provider, Vendor, Vehicle, Review, InventoryItem, etc. |
| AuditLog.entity | entity_type + entity_id | Any audited entity |
| ModerationCase.target | target_type + target_id | Review, Post, Comment, PortfolioItem, InventoryItem |

These should be implemented carefully with referential integrity rules and audit support.

# 17. Key Relationship Rules

## Identity rules

- A user can belong to multiple organizations.
- An organization can have multiple locations.
- An organization can have only one provider profile, one vendor profile, and one fleet profile.
- A hybrid organization may enable both provider and vendor profiles.

## Vehicle rules

- A vehicle must have exactly one owner type:
  - individual user, or
  - organization/fleet.
- A vehicle can have many service records and issues.
- A fleet vehicle may be assigned to one active driver at a time.

## Provider rules

- A provider profile can declare unlimited services and vehicle coverage.
- Capabilities should be evidence-backed.
- Capability evidence can reference:
  - completed appointments
  - service records
  - portfolio items
  - reviews
  - certifications
- Skill heatmap entries are AI-derived and should not be treated as source-of-truth.

## Vendor rules

- Inventory items belong to one vendor organization.
- Inventory fitment can have multiple compatible vehicle entries.
- Fitment confidence must be tracked.
- Vendor inventory is tenant-isolated.

## Review rules

- A review has one author and one subject organization.
- A review may optionally reference a vehicle, appointment, or service record.
- Verified reviews should reference a trust context.
- A review can have one official provider/vendor response.

## Appointment rules

- An appointment always references:
  - requester
  - provider organization
  - vehicle
- A pre-visit report is optional but recommended.
- Completed appointments can generate service records and review invitations.

## AI/MCP rules

- AI insights are separate from source-of-truth records.
- AI suggestions require acceptance before becoming public or operational.
- MCP access logs must reference client, principal, operation, and context.
- Approval requests are required for public or high-risk actions.

# 19. Minimal MVP Relationship Priorities

If implementation needs to be phased, these are the most critical relationships.

## Phase-critical relationships

1. `UserAccount` ↔ `Organization` through `RoleMembership`
2. `Organization` ↔ `ProviderProfile` / `VendorProfile` / `FleetProfile`

4. `Vehicle` ↔ `VehicleServiceRecord`
5. `Vehicle` ↔ `Appointment`
6. `Organization/Provider` ↔ `Appointment`
7. `UserAccount` ↔ `Review` ↔ `Organization`
8. `ProviderProfile` ↔ `ProviderCapability`
9. `ProviderCapability` ↔ `ProviderCapabilityEvidence`
10. `VendorProfile` ↔ `InventoryItem` ↔ `InventoryFitment`
11. `TaxonomyNode` ↔ capability/fitment/category references
12. `McpClient` ↔ `McpAccessLog` ↔ `AiInsight`

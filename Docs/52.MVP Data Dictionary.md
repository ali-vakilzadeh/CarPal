# 1. Notation

| Symbol | Meaning |
|---|---|
| R | Required |
| O | Optional |
| C | Conditional (the rule column says when it is required) |
| S | System-generated (clients cannot set it) |

Logical types:

| Type | Meaning | PostgreSQL storage |
|---|---|---|
| ID | Globally unique identifier | `uuid` (UUIDv7 recommended for index locality) |
| string | Short text | `text` with length check |
| text | Long text | `text` |
| translations | Map of locale → text, e.g. `{"en": "Brake Pad", "fa": "لنت ترمز"}` | `jsonb` + GIN index where searched |
| integer / decimal | Numbers | `integer` / `numeric` |
| money | Amount + ISO 4217 currency, always as two fields | `numeric(12,2)` + `char(3)` |
| boolean | True / false | `boolean` |
| date / time / datetime | Calendar date / time of day / instant | `date` / `time` / `timestamptz` (UTC) |
| enum | Value from a list in this document | `text` + check constraint, or PostgreSQL enum |
| reference | ID of another record in the **same module** | `uuid` + foreign key |
| xref | ID of a record owned by **another module** | `uuid`, no cross-module foreign key (Plan §14.5) |
| list | Ordered list of values | `jsonb` array or `text[]` |
| structured | Machine-readable object | `jsonb` |
| vector | Embedding | `vector(n)` (pgvector) |

## 2.4 Multi-language fields (Plan §3.3)

| Rule | Detail |
|---|---|
| Enabled locales | `en`, `fa` at launch. A new locale is added by configuration, never by schema change. |
| Translatable fields | Named `<field>_translations`, type `translations`. Used for platform-curated and business-authored catalog content (see list below). |
| Required locales | **Platform-curated** fields (taxonomy labels): `en` and `fa` both required. **Business-authored** fields (profiles, inventory): at least one locale required. |
| Read rule | API returns the `Accept-Language` locale, then falls back to `en`, then to the first available locale. |
| Indexing | GIN index on every `_translations` column used in search or filtering (Plan §14.3). |
| User-generated content | Reviews, posts, comments, questions, answers and notes are **not translated**. They store the author's language in `content_locale`. |
| UI text | Platform UI text, notification templates, plan names and badge titles are **not** stored in the database. They live in the UI dictionary (`shared/i18n/locales/*.json`) and are referenced by key. |

Translatable fields: `TaxonomyNode.name/description`, `Organization.description`, `OrganizationLocation.access_instructions`, `ProviderProfile.description/warranty_policy`, `ProviderServiceCategory.display_name/description`, `VendorProfile.description/return_policy/warranty_policy`, `InventoryItem.name/description`.

## 2.5 Regional formats (Plan §3.4)

| Data | Storage rule | Display rule |
|---|---|---|
| Timestamps | UTC `timestamptz` | User timezone; Gregorian or Jalali calendar per `UserPreference.calendar_system` |
| Money | Amount + ISO 4217 currency code | Local currency format |
| Digits | Latin digits only. Persian (۰–۹) and Arabic-Indic (٠–٩) digits are converted on write. | Persian or Latin digits per `UserPreference.digit_style` |
| Phone | E.164 | Local format |
| Country | ISO 3166-1 alpha-2 | Localized name from UI dictionary |
| Address | Structured fields (§5 OrganizationLocation) | Local address order |
| Distance and mileage | Kilometres (`*_km`) | km or miles per `UserPreference.distance_unit` |
| Persian text | Unicode NFC. Arabic `ي`/`ك` normalized to Persian `ی`/`ک` in search and normalized fields. Zero-width non-joiner (ZWNJ) preserved. | As stored |
| Search text | Normalized before matching and before it is stored on `MatchSession`: character variants, Persian and Arabic-Indic digits to Latin digits, spacing marks, extra whitespace. Persian typed in Latin letters is mapped to taxonomy terms through `TaxonomySynonym` (`synonym_type = transliteration`). New languages are added through synonyms and analyzers, never through code (Plan §3.5). | As typed, with the interpretation shown as editable chips |
| Map and geo | Coordinates as WGS84 decimal degrees. Distances shown on cards are straight-line and labelled approximate. Directions are deep links to external map apps and carry only the destination. | Map labels follow the app language |

**Region configuration is not stored in the database.** Tile region, geocoder region, label languages, navigation app list, distance units, address format, currency and calendar live in `shared/` and `geo/` region configs (Plan §3.5, §9.7). Pilot (pre-seed): Iran. Main launch: USA or Euro zone. A user's remembered navigation app is stored in `UserPreference.navigation_app_key` and validated against the region's list.

## OrganizationLocation

| Field | Type | Req | Validation / Rule |
|---|---|---|---|
| `organization_id` | reference | R | Must exist |
| `name` | string | O | 2–120 chars |
| `address_line_1` | string | R | 2–160 chars |
| `address_line_2` | string | O | Max 160 chars |
| `city` | string | R | Max 100 chars |
| `region` | string | O | Max 100 chars |
| `postal_code` | string | O | Max 20 chars |
| `country` | string | R | ISO 3166-1 alpha-2 |
| `latitude` | decimal | C | −90 to 90; required for geo search and the map |
| `longitude` | decimal | C | −180 to 180; required for geo search and the map |
| `geo_source` | enum | R | Geo source: `user_pin` (placed by the owner on the map during onboarding), `geocoded` (from the typed address), `admin_corrected` |
| `geo_address_distance_m` | integer | S | Distance between the owner's pin and the geocoded typed address. Computed on save. |
| `location_check_status` | enum | S | not_checked, consistent, far_apart. `far_apart` when the distance is above the region threshold (proposed 300 m in cities; set per region). |
| `public_address_visibility` | enum | R | Public address visibility. Default `exact`. `approximate` is for home-based and mobile providers. |
| `public_latitude` / `public_longitude` | decimal | S | Rounded point used on public maps and cards when visibility is `approximate`; equal to the exact point otherwise. The exact point is never returned by public APIs for an approximate location. |
| `timezone` | string | R | IANA timezone |
| `service_radius_km` | integer | O | 0–1000. A **circle** around the location. Service-area polygons are Phase 2+. |
| `phone` | string | O | E.164 |
| `email` | string | O | Valid email |
| `primary_contact_user_id` | xref | O | Organization member |
| `access_instructions_translations` | translations | O | Max 500 chars per locale |
| `hours` | structured | O | Weekly opening hours + exceptions |
| `location_verified_at` | datetime | S | Set when location verification passes |
| `is_primary` | boolean | R | Exactly one primary per organization |
| `status` | enum | R | active, inactive |

Rules:
- The owner places a pin on the map (OpenStreetMap) during onboarding. The platform compares it with the geocoded address and sets `location_check_status`; a `far_apart` result warns the owner and is shown to the verification reviewer. It does not block saving.
- A location with `public_address_visibility = approximate` shows only `public_latitude`/`public_longitude` and a service radius circle. The exact address is shared with the requester only after the appointment reaches `confirmed`.
- Staff can move the pin or correct the address with a reason (`geo_source = admin_corrected`). The change is written to `AuditLog` and the organization is notified.
- Users can report a wrong location or a closed business. The report is a `ContentReport` with `target_type = organization_location` and reason `wrong_location_or_closed`, surfaced in the verification queue.
- Map pins carry public fields only: no trade prices and no private data. There is one pin per location, never one per part.

Rules:
- Users cannot review an organization they belong to. One review per user per appointment, service record or inquiry context.
- **Two alternative confirmation paths (MVP Module F).** A review confirmed in neither way is never published.
  - **Path 1, visit-based:** the author's appointment with the subject was confirmed and took place (§21). After the automatic safety and abuse checks the review is published as `appointment_verified` (or another Path 1 status). **The business does not approve it and cannot block it.** It can reply publicly, report the review or open a dispute; removal needs an audit reason.
  - **Path 2, approval-based:** no appointment link, or written after the 7-day invitation window. The review starts as `status = pending_approval`, `verified_status = pending_approval`, hidden. It is published only after **both** (1) the business confirms the author was its customer (a yes/no/do-not-recognise decision about the relationship, not the opinion; no answer in 7 days, or no active account, means no objection; a business-sent invitation counts as confirmed) and (2) a CarPal reviewer approves. It then becomes `approved_without_visit`, labelled "Approved by the business and CarPal", at a lower weight.
  - If the business rejects the relationship, the review is **not** removed or published automatically. A `Dispute` with `dispute_type = review_approval_objection` is opened; the author can add evidence (invoice, photo via `MediaAttachment` role `evidence`); a different staff member from the first reviewer decides. If upheld the review is published with `disputed_by_business = true`.
  - A rating alone is never a reason to reject or remove.
- There is **no separate "unverified" section**. Both labels ("Verified visit", "Approved by the business and CarPal") count toward the score; Path 2 counts for less (weight in [54 §1.2](54.Scoring%20Protocol.md)).
- A Path 1 review whose appointment evidence is found invalid can be moved to Path 2 by a T&S lead (four-eyes), which returns it to `pending_approval`.
- The review approval states here are not the same as AI `ApprovalRequest` (§19), which gates AI-generated actions.
- Review velocity limits apply per author and per subject (values in the WP0 trust rules).
- Removed reviews are kept for audit and hidden publicly.

# 21. Cross-Entity Validation Rules

## Vehicle limits
- Active vehicles (status `active` or `in_repair`) cannot exceed `max_vehicles` from the subscriber's plan: Individual Free 5, Fleet 20/50/100, Fleet Custom by override.

## Organization publish rules
A provider can be public only if: organization `active`; ≥1 active location; provider profile complete enough; ≥1 active service category; ≥1 supported brand.

A vendor can be public only if: organization `active`; ≥1 active location; vendor profile complete enough; ≥1 active inventory item, or the profile is explicitly marked "catalog coming soon".

## Review trust rules
**Path 1, visit-based (no shop approval):**
- `appointment_verified`: the appointment exists, reached `confirmed`, its scheduled time has passed, it was not `cancelled` or `no_show`, and the author is the requester or a participant. Normally the shop has moved it to `completed`; if the shop forgot to close it, the review is still allowed 24 hours after the scheduled time. The review must be written within 7 days of the invitation being sent (`ReviewRequest.expires_at`).
- `inquiry_verified`: the stock inquiry is `completed` (closed by either side) and the author is the requester.
- `service_record_verified`: the service record has `verification_status` other than `self_reported` and belongs to the author's vehicle.
- `invoice_verified`: an invoice `VehicleDocument` or `ServiceRecordEvidence` exists, is linked to the vehicle or service record, and the author's consent allows verification use.
- `fleet_confirmed`: fleet appointment completed and confirmed by a fleet manager.
- `admin_verified`: staff verified the visit evidence.

**Path 2, approval-based:**
- `pending_approval` → `approved_without_visit`: the review has no qualifying visit evidence, or was written after the 7-day window. It is published only when `business_confirmation_status` is `confirmed` or `no_response` (7 days passed, or no active business account) **and** `reviewer_decision = approved`.
- A job the provider logged and sent an invitation for (no appointment) is Path 2 with `business_confirmation_source = business_invited`; the CarPal reviewer still approves.
- A rejected business confirmation never publishes or removes the review by itself; it opens a `review_approval_objection` dispute (§11).

## Search and map rules
- Free-text search must work without AI and without Help Me. Safety words in search text or request text set `safety_flag` and show the banner; results stay visible.
- Map pins use public fields only, one pin per business location. No featured or paid pin is ever returned (`MatchResult.is_sponsored` is false and `featured.enabled` is off in the MVP).
- A location with `public_address_visibility = approximate` never exposes its exact coordinates or street address to unconfirmed users.

## Appointment rules
- Confirmation needs: provider accepted or the requester accepted the proposed alternative; `confirmed_start_at`; vehicle context; consent if history is shared; capacity available.
- Completion needs: the appointment passed through `confirmed` or `checked_in`; `completed_at`; an outcome or service record.

## Inventory rules
- Public item: vendor profile published; item `active`; category; name; public price or price on request.
- Confirmed fitment: vendor confirmation, or trusted structured data later.

## Media and consent rules
- Public portfolio, showcase or post media follow the MediaAsset public rules (§15) and the consent rules (§4).

## AI/MCP rules
- AI output affects public data only through an approved `ApprovalRequest` or an accepted `AiSuggestion`. Policy may mark an action low-risk only if it is non-public.
- AI suggestions can be accepted only if the target exists, the user may modify it, and the suggestion is still pending.
- The AI kill switch blocks every AI write tool.

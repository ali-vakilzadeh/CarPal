# 1. Shape of the Backend

The backend is a **modular monolith with event-driven AI/MCP services** (Plan §1). One TypeScript/NestJS codebase produces several deployables; the AI side is two separate services that the monolith calls.

| # | Deployable | Entry point | Reached from | Contents |
|---|---|---|---|---|
| D1 | **Auth server** | `apps/auth` | `id.carpal.app` | OAuth 2.1 / OIDC authorization server, hosted sign-in UI endpoints (`/oauth/*`, `/v1/auth/*`, `/.well-known/*`) |
| D2 | **Public API** | `apps/api` | `api.carpal.app`, consumer and portal BFFs | Every domain module, all `{me}`, `{org}`, `{pub}` operations of 40 |
| D3 | **Admin API** | `apps/admin-api` | `admin-api.carpal.app` (private network only) | The same modules with the admin plane (`{adm}`) registered; no consumer routes |
| D4 | **BFFs** | `apps/bff-consumer`, `apps/bff-portal`, `apps/bff-admin` | `app.`, `business.`, `admin.carpal.app` | Session cookie ↔ token, CSRF, same-origin forwarding 1:1 (40 SEC-WEB) |
| D5 | **Workers** | `apps/worker` (one image, worker set chosen by env) | NATS JetStream, BullMQ, scheduler | Event consumers and background jobs (§6) |
| D6 | **MCP Gateway** | `ai-mcp/mcp-gateway` | Internal only (API, workers, AI orchestration) | Registry, resource and tool catalog, policy engine, tool executor, MCP access log |
| D7 | **AI Orchestration** | `ai-mcp/orchestrator` | Internal only (MCP gateway, AI workers) | LLM routing, prompt registry, context builder, insight and evaluation store, vector access |
| D8 | **Geo services** | infrastructure | API (geocoder), clients (tiles via CDN) | Self-hosted geocoder (Nominatim or Photon), tile files; not NestJS code |

Rules that shape the code:

1. **One module owns each table** and is the only code that writes it (50 §2). Cross-module references are IDs with no foreign keys, validated through the owning module's interface (Plan §14.5).
2. **Modules talk in two ways only:** synchronous calls to another module's exported service interface (in-process), and domain events through the transactional outbox (asynchronous). No module imports another module's repositories or entities.
3. **Each module has its own PostgreSQL schema** (§3), so a module can later move to its own database without a redesign.
4. **AI never reads domain tables.** AI features call MCP tools; MCP resources are served by the owning modules' interfaces (Plan §5.5, 40 SEC-AI-1).

Notes per module:

- **identity** also runs the authorization server's account logic (D1 uses the identity module's services). Sessions, refresh-token families, OTP codes, WebAuthn challenges, review `invitation_grant`s and idempotency records live in Redis (52 §4).
- **organization** contains three sub-packages that keep the large module readable: `org-core` (organization, members, locations, verification, geo adapter), `provider` (WP6) and `vendor` (WP7).
- **billing** exposes `EntitlementService.check(subscriber, key, delta)` used by vehicle, inventory, fleet, appointment and ai-mcp inside their write transactions (40 SEC-AZ-9).
- **taxonomy** exposes the cached `TaxonomyResolver` (node type and parent-chain checks for `NodeId<type>`, label resolution, synonyms for the query interpreter) used by almost every module.
- **discovery** writes no domain data except match sessions and results. It reads Elasticsearch projections maintained by the search-indexer worker, and runs the rule-based query interpreter and the shared **safety keyword check** (also called by vehicle, appointment and ai-mcp).
- **trust** runs the two review paths (52 §11, §21) and is the only writer of trust scores and badges (through its workers).
- **appointment** owns the calendar and capacity check; confirmation locks the provider's capacity rows inside the transaction (52 §12).
- **media** issues pre-signed upload and download URLs; scanning, re-encoding and redaction run in the media-processor worker.
- **ai-mcp (API facade)** is the thin module inside the API that turns §21 operations into MCP tool calls and stores results; the MCP gateway (D6) and orchestrator (D7) are separate services that share its schema through their own DB roles (§3.3).

# 5. Request Lifecycle

Every API operation goes through the same pipeline, in this order:

1. **Edge** — TLS 1.3, WAF, path and framing checks, coarse limits.
2. **Router** — only operations declared in 40 are registered; unknown route → `404`.
3. **Transport checks** — `CarPal-Client`, content type, body ≤ 64 KiB, strict JSON parse, closed schema, Unicode normalization (L2).
4. **Authentication** — token signature, `aud`, DPoP or mTLS binding, `sid` live in Redis, `acr` for step-up (L3).
5. **Rate limit** — bucket(s) from `RL(...)` and the tag default; `429` with retry delay (L8).
6. **Authorization** — role from server state; `ORG`, `DRV`, `STF`, `PURP` guards; path tenant must match; failures are `404` (L4).
7. **Feature flags and entitlements** — `FLAG(key)`; `ENT(key)` is re-checked inside the transaction (L14, L17).
8. **Idempotency / ETag** — replay or conflict handling before any write (L6, L7).
9. **Transaction** — `BEGIN`; set RLS context (L5); run the use case; consent gates on reads (L16); body references checked through owning interfaces (`422 REFERENCE_NOT_FOUND`); state machine checks with row locks; write; `AUD` entry (L15); outbox events (L9); `COMMIT`.
10. **Projection** — build the response from the audience allowlist (public, member, staff); `ETag`; `Cache-Control`.
11. **After commit** — outbox relay publishes events; workers react.

Admin API requests add: `aal3` session, `RSN` reason, `PURP` purpose header bound to an item in the caller's queue, PII read-audit, and the four-eyes path (`PendingAdminChange`, executed by the same use case on approval).

# 6. Events, Workers and Schedules

## 6.1 Event flow

```text
use case ──(same transaction)──► core.domain_event_outbox
                                      │ W1 outbox-relay
                                      ▼
                               NATS JetStream streams (one per module)
                                      │ durable consumers, de-dup on event_id
      ┌───────────────┬───────────────┼───────────────┬───────────────┐
      W2 search       W3 trust         W5 notify       W9 AI insight   W12 analytics …
```

Stream names: `evt.<module>` (e.g. `evt.trust`). Subjects: the event type (e.g. `review.published`). Consumers are idempotent; a failed message is retried with backoff and then parked in a dead-letter stream with an alert.

| Schedule | Rule | Module |
|---|---|---|
| every 5 min | Path 2 reviews past `business_confirmation_due_at` → `no_response`, move to reviewer queue | trust |

# 7. Cross-Cutting Implementation Notes

| Topic | Implementation |
|---|---|
| **IDs** | UUIDv7 generated in the application (`core.uuid_v7()` as DB default) |
| **Optimistic concurrency** | `version` incremented by trigger; `ETag: "v<version>"`; updates use `WHERE id = $1 AND version = $2` |
| **State machines** | Appointment, inquiry, review, approval and dispute transitions are coded in `domain/` and also guarded by DB triggers (42) |
| **Tenancy** | Path tenant (`org_id`) → RLS context → owner predicates in every query; RLS is the second wall (40 SEC-AZ-3) |
| **Cross-tenant reads** | Only through owning-module interfaces: minimal projections (vehicle card, user display card) via `SECURITY DEFINER` functions, consent-gated data copied by workers (e.g. pre-visit history) |
| **Consent** | Checked on every read of shared data; withdrawal emits `consent.withdrawn`; consent-gated copies are cleared by consumers |
| **Entitlements** | Counted inside the write transaction with a row lock on the subscription (`SELECT … FOR UPDATE`) |
| **Translations** | `jsonb` maps validated by `core.translations_valid`; reads resolve with `core.l10n()` or the L13 library |
| **Encryption** | VIN, invited contacts, push tokens, document keys: AES-256-GCM envelope in L11; ciphertext in `bytea`; hashes for lookup |
| **Link tokens** | Only HMAC hashes stored; consumption is one conditional `UPDATE … WHERE used_at IS NULL` |
| **Audit** | `AUD` writes `analytics.audit_logs` in the same transaction; table is append-only (trigger + grants) |
| **Search** | Fixed match-family queries; text normalized with the same rules as `core.normalize_search_text()`; trade prices never indexed |
| **Geo** | No PostGIS in the MVP; geo queries run in Elasticsearch; DB stores WGS84 decimals and computes the public point by trigger |
| **AI degradation** | Kill switch and per-feature flags return `503 AI_UNAVAILABLE`; search, profiles, appointments, safety check stay rule-based |
| **Observability** | Trace ID = `CarPal-Request-Id`; per-module metrics (latency, errors, outbox lag, consumer lag, job duration, AI cost) |

# CarPal MVP — Admin Web UI Screen List

**App:** CarPal admin console, Next.js, internal staff only (Plan WP15, WP17, WP20; `frontend/admin-console/`).
**Users:** CarPal platform staff (moderators, verification officers, trust and safety, privacy, AI governance, support, platform admins).
**Lens:** every admin task that Sara's journey in [10.User Story - Car Owner](10.User%20Story%20-%20Car%20Owner.md) depends on is traced to a screen (see §5). Admin tasks from the [mechanic](11.User%20Story%20-%20Repair%20Mechanic.md) and [vendor](12.User%20Story%20-%20Parts%20Vendor.md) stories (verification, certifications, inventory flags) are included so the console is complete.
**Builds on:** [90.CarPal Screen Map](90.CarPal%20Screen%20Map.md) §9 (admin screen IDs), [52.MVP Data Dictionary](52.MVP%20Data%20Dictionary.md) (ModerationCase, ModerationAction, Dispute, DataSubjectRequest, ConsentRecord, FeatureFlag, AuditLog, McpAccessLog), [54.Scoring Protocol](54.Scoring%20Protocol.md) (badges and trust weights), [53.MCP Catalog](53.MCP%20Catalog.md).
**User-facing screens:** [21.Mobile_app_screen_list](21.Mobile_app_screen_list.md), [22.Social_WebUI_user_screens](22.Social_WebUI_user_screens.md).

**How to read each screen:** Purpose · Who (staff roles) · Layout · Elements (table columns, filters, panels) · Actions (with confirmation and reason rules) · States · Audit · Story link.

Screen IDs marked **(new)** are not in Doc 90. They are listed in §7 for WP0 approval.

## 1. Admin principles

| # | Principle | What it means on screen |
| :--- | :--- | :--- |
| 1 | **Every action has a reason** | Any action that changes a user, organization, review, content, plan, flag or AI setting opens a reason panel: a reason code (required) and a note (required for removals, suspensions and rejections). No reason, no action (WP15 acceptance). |
| 2 | **Everything is audited and visible** | Every entity page has an **Audit trail** drawer showing who did what, when, and why. Staff can see their own actions in "My actions". |
| 3 | **Humans decide, AI assists** | AI risk scores, flags and summaries are shown as labelled inputs ("AI risk 82 — reasons: …"). AI never closes a case or removes content by itself (MVP §7.5D). |
| 4 | **Least privilege, least exposure** | Staff see only what their role needs. Personal data (phone, email, full name, VIN, plates, documents) is masked by default; **Reveal** requires a reason and is logged. Private documents and media are never shown unless a case requires them. |
| 5 | **Queues, not searches** | Daily work starts from queues with SLA timers, sorted by severity and age. Search is for lookups. |
| 6 | **Context on one screen** | Case screens show the item, its context (author history, linked appointment, previous cases) and the action panel side by side, so the moderator never has to open five tabs. |
| 7 | **Reversible where possible** | Hide before remove; restore is available for removed content and reviews; suspensions have end dates by default. Irreversible actions (deletion of personal data, merging organizations) need a second confirmation, and some need a second staff member (four-eyes). |
| 8 | **The public sees fair outcomes** | Every decision that affects a user or business sends them a notification with the reason category and an appeal route. Templates are fixed and translated; staff add an optional note. |
| 9 | **Dense but readable** | Tables with fixed headers, column choice, saved views, keyboard navigation (`J`/`K` next/previous, `A` approve, `R` reject, `E` escalate, `/` search). EN and FA with RTL. |
| 10 | **Safety first** | Cases involving unsafe repair advice or safety-critical issues are always `high` or `critical` severity and go to the top of every queue. |

## 2. Staff roles and permissions

| Role | Main screens | Can | Cannot |
| :--- | :--- | :--- | :--- |
| **Content moderator** | Review queue, content queue, inventory queue, disputes (assigned) | Approve, hide, remove, restore content; warn users; request changes; escalate | Suspend accounts; verify organizations; change plans or flags; reveal documents |
| **Verification officer** | Verification queue, organization detail | Verify, reject, request info for organizations and certifications; reveal business documents | Moderate reviews; change plans |
| **Trust & Safety lead** | All moderation queues, disputes, user/org detail, scoring overrides | Everything moderators can, plus suspend/reactivate accounts, revoke badges, apply trust penalties, decide appeals, four-eyes approvals | Change feature flags or MCP clients |
| **Privacy officer** | Data subject requests, consent lookup, retention | Process export, deletion, rectification; view consent history; manage retention policies | Moderate content |
| **AI governance** | AI oversight, AI suggestion review, triage quality, MCP clients, MCP audit, AI flags | Review AI outputs, flag prompts, change AI feature flags, use the AI kill switch, manage MCP clients | Moderate user content directly (escalates instead) |
| **Support agent** | Support inbox, user lookup (read-only), organization lookup (read-only) | View accounts with masked data, resend verification, reset onboarding, open cases on behalf of users | Any moderation or enforcement action |
| **Commercial admin** | Plans & entitlements, featured placements | Assign plans, trials, overrides; manage featured placements | Change organic ranking; moderate |
| **Platform admin** | Staff & permissions, feature flags, policies, notification templates, all read access | Manage staff roles, flags, policy versions, templates | Bypass four-eyes rules; edit audit logs (no one can) |

A staff member can hold several roles. The left navigation shows only permitted sections. Opening a forbidden URL shows the no-permission state with "Request access" (creates an access request for a platform admin).

## 3. Console shell

### 3.1 Layout

| Area | Elements |
| :--- | :--- |
| **Top bar** | Environment badge (DEV / STAGING / **PROD** in red); global search (users by phone/email/ID, organizations by name/ID, any record by ID such as `appt_…`, `rev_…`); **My queue** button with count; notifications; staff avatar menu (my actions, language, sign out). |
| **Left navigation** | Dashboard · Users · Organizations · Verification · Reviews · Content · Inventory · Disputes & Appeals · Privacy Requests · Taxonomy · AI Oversight · MCP & Audit · Plans & Entitlements · Featured Placements · Notifications & Templates · Policies & Consent Texts · Feature Flags · Data Retention · Analytics · Audit Log · Support · Staff. Queue sections show live counts and turn amber/red when SLA is at risk. |
| **Main area** | List → detail. Queues use a three-panel case layout (§3.2). |
| **Audit drawer** | Available on every entity and case page (`Shift+H`). |

### 3.2 Standard case layout (all moderation queues)

| Panel | Width | Content |
| :--- | :--- | :--- |
| Left: queue list | 320 px | Cases with severity colour, type, age, SLA timer, AI risk score, assignee. Filters and saved views at the top. |
| Centre: item and context | flexible | The item exactly as the public sees it (with a "public view" link), then context blocks: author summary and history, target summary (e.g. the shop), linked appointment or service record, related reports, previous cases on the same item or author, AI analysis (labelled). |
| Right: decision panel | 360 px | Allowed actions as buttons; reason code select; note; "Notify author" preview (template + optional note, in the author's language); **Confirm**. Below: case history and internal notes. |

**Case rules:** opening a case assigns it to the viewer (with "Unassign" option); two staff cannot act on the same case at the same time (the second sees "Being handled by …"); every action writes `ModerationAction` + `AuditLog`; closing requires a resolution text (max 1000 chars, `ModerationCase.resolution`).

### 3.3 Shared components

| Component | Behaviour |
| :--- | :--- |
| Reason panel | Reason code (from `ModerationCase.reason` enum), note, notify toggle (on by default), template preview. |
| Masked field | Shows `+98 912 *** 4567`; **Reveal** asks for a reason and logs `pii.revealed` in the audit log. |
| Four-eyes request | For listed actions, the first staff member submits; a second eligible staff member approves or rejects from "Pending approvals". |
| Entity chip | Clickable chip for any linked entity (user, org, appointment, review), opens a preview popover and a link to its page. |
| AI evidence block | AI label, model/prompt version, risk score, top reasons, link to the MCP access log entry. |
| Bulk actions | Only for low-risk actions (approve, assign, tag). Removals and suspensions are never bulk. |

### A-AUTH-01 — Staff Sign-in (new)

**Purpose:** secure access for staff.
**Elements:** company SSO button (primary); fallback email + password; **MFA required** for every staff account (authenticator app or security key); IP allow-list notice for production; session timeout after 30 minutes idle with a warning at 25 minutes.
**States:** MFA not set up (forced setup); account disabled; access from a non-allowed network ("Use the company VPN").
**Audit:** every sign-in, failure and session end.

### A-DASH-01 — Admin Dashboard

**Purpose:** a single view of platform health and where staff are needed today.
**Who:** all staff; widgets filter to the viewer's roles.

**Layout and widgets**

| Row | Widget | Content | Click-through |
| :--- | :--- | :--- | :--- |
| 1 | **My work** | Cases assigned to me, SLA at risk, pending four-eyes approvals for me. | Filtered queue |
| 1 | **Queues** | Count and oldest item age per queue: verification, reviews, content, inventory, disputes, privacy requests, AI flags. Red if any SLA breached. | Queue |
| 2 | **Safety** | Open cases with reason `unsafe_advice` or severity `critical`; safety-critical triage sessions in the last 24 h (count only). | `A-CON-01` / `A-AI-03` |
| 2 | **Growth today** | New users, vehicles added, new organizations, appointment requests, completed appointments, reviews published. | `A-ANL-01` |
| 3 | **Trust** | Reviews published vs. pending vs. removed; fraud flags; review velocity alerts. | `A-REV-01` |
| 3 | **AI** | Suggestion volume, acceptance rate, override rate, hallucination reports, kill switch status (green "AI automation on" / red "AI automation OFF"). | `A-AI-01` |
| 4 | **System** | Inventory import failures, notification delivery failures, media scan failures. | Related screen |

**Controls:** date range (today, 7 days, 30 days); region (city) filter; refresh every 60 s.
**States:** no data for the range; widget error (shows the widget with Retry, others keep working).

### A-USR-01 — User List

**Purpose:** find a user account quickly.
**Columns:** user ID; display name; masked phone/email; status (`pending_verification`, `active`, `suspended`, `deactivated`, `deleted`); roles; organizations; vehicles count; created date; last active; open cases count.
**Filters:** status; role; country; created date; has open cases; has open privacy request; verified contact yes/no.
**Search:** by full phone or email (exact match, logged), user ID, display name.

### A-VER-02 — Verification Review (new)

**Layout:** three panels. Left: submitted data (business name, registration number, address, phone verification result, owner). Centre: document viewer (zoom, rotate, page through; watermark "CarPal internal"). Right: checklist and decision.
**Checklist:** business details match document; address exists (map check); contact verified (call-back code done); taxonomy consistency (claimed services make sense for the business type); no duplicate organization; for certifications: issuer recognised, name matches, date valid.
**Actions:** **Approve** (sets `verified`; profile shows Verified Business), **Request more info** (choose missing items; message template; status stays `pending`, SLA pauses), **Reject** (reason code + note required; organization notified with what to fix).
**Audit:** decision, checklist state and documents viewed.

**Columns:** review excerpt; rating; subject organization; author display name; verified status; AI risk score; reasons (e.g. "possible private data", "abusive language", "rating burst"); reports count; age; SLA; assignee.

### A-REV-02 — Review Case Detail (new)

**Centre panel content**
- The review as published (or pending), with sub-ratings, tags (marked AI-suggested and confirmed), photos, language.
- **Verification evidence:** linked appointment (status history ending in `completed`), service record, or invoice evidence; `verified_status`, `trust_weight`, `counts_toward_core_score`.
- **Author context:** account age, verified contact, number of reviews, distribution of ratings, previous removals, other reviews of the same business, shared device/network signals (summarised, no raw IPs unless revealed).
- **Business context:** recent rating trend, other reports, the business's reply and dispute text.
- **AI analysis** (labelled): sentiment, complaint flags, privacy detection, fake-review risk with reasons.

**Actions**

| Action | Effect | Rule |
| :--- | :--- | :--- |
| Approve / Keep | Review stays or becomes published; reports resolved | Reason code "no violation" accepted |
| Edit request | Asks the author to remove specific content (e.g. a plate number); review hidden until fixed or 7 days | Template + highlighted text |
| Hide | Hidden from public, kept for review | Note required |
| Remove | Removed publicly, kept for audit (`removed`); evidence revoked; scores recalculated (Doc 54) | Reason code + note required; author and business notified |
| Reduce weight | Keeps review visible but lowers `trust_weight` (e.g. suspected incentive) | T&S lead only; note required |
| Change verified status | e.g. from `appointment_verified` to `unverified` if evidence is invalid | T&S lead only; four-eyes |
| Restore | Reverses a removal | Note required |
| Escalate | Moves to T&S lead | Note required |

**Rule:** a low rating alone is never a reason to remove. The decision panel shows this reminder when the business is the reporter.

### A-DSP-01 — Disputes & Appeals (new)

**Purpose:** one place for disagreements that need a human decision: review disputes from businesses, service record corrections, badge challenges, moderation appeals, mediation requests.
**List columns:** dispute type (`fake_review`, `inaccurate_review`, `mediation_request`, `badge_challenge`, `service_record_dispute`, `moderation_appeal`); target; raised by (user or organization); status (`open`, `in_mediation`, `resolved_upheld`, `resolved_rejected`, `withdrawn`); age; assignee.

**Detail layout:** statement from the person who raised it; the target entity; the original decision (for appeals, with the decision-maker hidden from the appellant but visible to staff); evidence from both sides; message thread with each party (templated messages, separate for each side); internal notes.
**Actions:** Uphold (reverse or correct the target: restore content, reactivate account, correct a service record, restore a badge); Reject (keep the original decision); Start mediation (both parties invited to add information, deadline); Withdraw on request.
**Rules:** an appeal is decided by a different staff member from the one who made the original decision (enforced). Outcomes feed trust signals (Doc 52 Dispute rule).
**Story link:** Ch. 3 (appeal after suspension), Ch. 5 (Sara reports a provider-created record naming the wrong car: `service_record_dispute`; staff correct or detach the record).

### A-AI-01 — AI Oversight Dashboard

**Purpose:** watch AI quality and safety across features.
**Widgets:** volume by feature (triage, matching explanations, maintenance suggestions, review tags, privacy detection, review response drafts, profile helper, showroom composer, inventory normalization); acceptance rate; edit-before-accept rate; override/correction rate (e.g. triage category changed by the user, MVP §16); hallucination and "unsafe advice" reports from users; moderator override rate of AI flags; latency and error rate; cost per feature; model and prompt versions in use.
**Controls:** feature filter; date range; language (EN/FA, since quality may differ); **AI kill switch** status with link to `A-FLAG-01`.
**Alerts:** threshold breaches (e.g. triage correction rate above target) shown as red cards with a link to examples.

### A-AI-02 — AI Suggestion Review

**Purpose:** inspect samples and flagged AI outputs.
**List columns:** suggestion type; feature; created; model/prompt version; user action (accepted, edited, dismissed); flagged by (user report, moderator, eval rule); risk level.
**Detail:** the context the AI received (minimized, as logged by MCP), the output, what the user did with it, and the MCP access log link.

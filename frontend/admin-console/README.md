# CarPal admin console

Internal staff console of CarPal (WP15 UI, WP20 admin part): Path 2 review approvals, moderation, disputes,
verification, privacy requests, plans, flags and the AI kill switch, the USD exchange rate, taxonomy, audit, AI/MCP
oversight and analytics. It is its own Next.js app with its own BFF for the `cp-web-admin` OAuth client (aal3,
audience `admin-api`) and is served only on `admin.<DOMAIN>` behind an access gate.

The build plan and stage log is [dev-plan.json](dev-plan.json). Sources of truth: `Docs/40.API contract.md`
(contract 1.3.0, §23 admin plane) for operations and security rules, `Docs/23.Admin_WebUI_screens.md` for screens.

Status: AC1 (foundation), AC2 (backend S12: staff sign-in, contract 1.3.0), AC3 (the BFF), AC4 (staff sign-in and
the console shell), AC5 (the admin interaction kit, Pending approvals and My work) and AC6 (platform settings:
exchange rates, feature flags and the AI kill switch, plans and assignments, data retention) are done; AC7 (reviews:
the Path 2 approval queue, review cases, disputes and appeals) and AC8 (moderation: the reports inbox, content,
account, AI output and inventory cases, badges) are built, their signed-in E2E waiting for a strict run with the
client key. The other sections in the navigation are placeholders until their stages (AC9 on).

## Environment

See [.env.example](.env.example). `CARPAL_ADMIN_ENV` (dev | staging | prod) drives the environment badge that is
always visible; outside dev the origin must be https, strict mode must be on and the `cp-web-admin` private key set.
`CARPAL_STORAGE_URL` (the storage host of signed media links; the page CSP allows it for images and video) and
`CARPAL_ADMIN_PUBLIC_WEB_URL` (the public web app, for "Open the public page" links) are https outside dev too (AC8).

## BFF

The browser holds one cookie of its own, `__Host-cpa_sid` (HttpOnly, Secure, SameSite=Strict, a browser-session
cookie). Tokens, the DPoP key and the staff profile stay in the server-side session.

| Path                                                  | What it does                                                                               |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `GET /bff/login?return_to=…`                          | Sign-in at aal3 (code + PKCE) through the console's own `/id` pages.                       |
| `GET /bff/reauth?return_to=…&intent=…`                | Step-up after STEP_UP_REQUIRED (prompt=login); the same staff member must sign in.         |
| `GET /bff/oauth/callback`                             | Code exchange (DPoP-bound, private_key_jwt), aal3 check, `admin.staff_me`, new session id. |
| `GET /bff/session`                                    | Who is signed in, roles, language, time zone, idle and absolute end. Never tokens.         |
| `GET /bff/csrf`, `POST /bff/logout`                   | CSRF token; sign-out (revokes the refresh token).                                          |
| `POST /bff/intents`, `POST /bff/intents/<id>/consume` | An action saved before a step-up, replayed once after it.                                  |
| `/api/v1/admin/*`                                     | The 63 admin-api operations of the generated map, 1:1; anything else 404.                  |
| `/id/oauth/*`, `/id/v1/auth/*`, `/id/.well-known/*`   | The auth host on this origin (sign-in steps, passkey enrolment).                           |

Sessions end after 30 minutes without an API call and 8 hours after sign-in (the backend's `cp-web-admin`
lifetimes). Writes need `X-CSRF-Token`, `Origin` and `Sec-Fetch-Site: same-origin`. Purpose-bound reads send
`CarPal-Access-Purpose: <case|dispute|dsr|verification|approval>:<uuid>` (the client refuses a PURP call without one);
DELETEs that need a reason send `CarPal-Reason`.

## Sign-in and the shell (AC4)

- Every page under `src/app/(console)` needs a staff session: without one the layout sends the browser to
  `/bff/login?return_to=<the page>`. A sign-in that failed comes back with `?signin=<outcome>` and, when nobody is
  signed in, goes to `/id/signed-out?reason=<outcome>` instead (no loops).
- `/id/signin` is the staff sign-in: work email + password (proof of work in strict mode), then the security key. An
  account without a device-bound key gets an emailed code and creates one in the same sign-in (the browser prompt),
  then confirms with it. "Sign in with a security key" uses the key alone; a step-up (`/bff/reauth`) shows it first.
  Synced passkeys are refused (SEC-ADM-2). No sign-up, no one-time-code sign-in, no social sign-in.
- At the first sign-in the BFF sets `cpa_locale` from the staff member's language, unless this browser chose one.
- The navigation shows the sections whose operations one of the caller's roles may call (`src/features/shell/sections.ts`
  over the generated role table). A section without access shows the no-permission state with the roles that may open
  it. Console pages render that state (and "not found") themselves: never call `forbidden()` or `notFound()` under
  `(console)` — in Next.js 16.4.3 they leave a blank page under the Trusted Types CSP (dev-plan D-26).
- Idle: a warning 5 minutes before the 30-minute end ("Stay signed in" makes an API call), then sign-out and
  `/id/signed-out?reason=idle`. The deadline is measured against the server's clock (`server_time` in `/bff/session`).
- Step-up: `useStepUp()` runs an action; on `STEP_UP_REQUIRED` it explains, saves the action (`/bff/intents`) and goes
  through `/bff/reauth`; back on the page, `useIntentHandler(type, …)` repeats it once.
- Keyboard: `useShortcut('next' | 'previous' | 'approve' | 'reject' | 'escalate' | 'audit', handler)` per page; `/` goes
  to the lookup box, `?` lists the keys. Off while typing and while a dialog is open.

## Admin kit (AC5)

Every console screen is built from `src/components/admin` so the admin rules hold everywhere:

- Writes: `useAdminAction(opId)` is the only way a screen sends a mutating operation. It refuses an RSN operation
  without a reason of 3–500 characters, runs it through the step-up (and repeats it once after the security key), and
  returns the outcome: applied, waiting for a second staff member (202 PendingChange: `FourEyesBanner`, remembered in
  memory as "your requests"), accepted job, or a problem (`ActionNotice` explains SELF_APPROVAL_FORBIDDEN, expired,
  changed meanwhile). The reason comes from `ReasonDialog`: a code from `src/lib/config/reasons.ts` for that kind of
  action plus a note (required for rejections, removals, suspensions and "Other"), sent as `"<code>: <note>"`.
  Irreversible actions pass `irreversible` (a second confirmation).
- Reads of private data: wrap them in `PurposeGate` (the work item comes from `?purpose=<kind>:<id>`; links keep it with
  `withPurpose`); `MaskedField` masks phone, email, names, VIN and plates and reveals through a purpose-bound re-read.
- Lists: `DataTable` + `useUrlFilters` (enumerated filters in the URL) + `useCursorPaging` (≤ 100 rows a page).
  Saved views and column choices stay in this browser and never hold data.
- Case screens: `CaseLayout` (queue 320 px / item / decision 360 px), `EntityChip`, `Timeline`, `AiEvidenceBlock`,
  `SlaBadge`, and `AuditDrawer` (Shift+H; ADM only, others see "Audit visible to platform admins").
- DOM tests render with `tests/support/console-harness.tsx` (providers, scripted transport, axe in jsdom) and mock
  `next/navigation` with `tests/support/navigation-mock.ts`.

## Platform settings (AC6)

Platform admins only (the other roles see the no-permission state).

- **Exchange rates** (`/rates`): the amount of each display currency per US dollar, which every app reads through
  config.client. This replaces the one-time SQL in `backend/deploy/deploy.md`. The editor previews sample prices
  and warns when a change is over 20 %; such a change waits for a second admin.
- **Feature flags** (`/flags`): the AI automation kill switch is a large control on top. Turning it on is immediate
  (reason and confirmation). Turning it off waits for a second admin. Every flag can be switched and its targeting
  edited (roles, regions, organization ids, plans, share of users). Turning `featured.enabled` on waits for a second
  admin and shows the MVP note.
- **Plans & entitlements** (`/plans`): plan edits send only the changed entitlements and always wait for a second
  admin. The plan's history is its audit trail (Shift+H). The assignment form gives one user or organization a plan,
  a trial (end day required) and limit or entitlement overrides. It applies at once. Other screens link to it with
  `/plans?subscriber=organization:<id>` or `user:<id>`.
- **Data retention** (`/retention`): policy edits always wait for a second admin. The contract has no add and no
  dry run, and the screen says so.

Writes that carry an ETag send the record's `version` from the list as If-Match (`ifMatchOf` in
`src/lib/api/client.ts`; lists have no per-record ETag header). A 412 shows "changed meanwhile" with a **Reload**
(`ActionNotice onReload`) that keeps what was typed.

My work (`/`) counts each queue from its list operation (at most two pages of 100 per status; "200+" beyond) and
colours it with the SLA targets of `src/lib/config/sla.ts`; the top bar's My queue shows the number of changes
waiting for the caller's approval.

## Reviews and disputes (AC7)

- **Reviews** (`/reviews`), two tabs by role. **Awaiting approval** (community reviewers decide; moderators read):
  Path 2 reviews by stage (waiting for a CarPal reviewer, for the business, for evidence), oldest first, with the
  2-working-day timer. A review opens for its approval purpose (`?review=<id>&purpose=approval:<id>`) with the
  business's answer and note, the author's history (no contact data) and evidence files (a short-lived link through
  `admin.media_download_url`, never inline). **Confirm** (A) is possible once the business confirmed or its 7 days
  passed; **Reject** (R, note required) and **Ask for evidence** work in every stage. The reason code is sent as
  `reason_code` and none of the codes is a rating. A business objection shows a link to its dispute.
  **Review cases** (moderators, platform admins): reported, AI-flagged and rule cases on reviews; a case opens for its
  purpose and offers the actions that fit the review's state (approve a held-back Path 1 review, remove, restore,
  warn the author), **Move to the approval path** (four-eyes, a second moderator decides it on Pending approvals) and
  **Close the case** with an outcome and a resolution.
- **Disputes & appeals** (`/disputes`): open disputes by type and assignment (`?type=…&assigned=mine|unassigned`); a
  dispute opens for its purpose with the statement, who raised it and, for a review, the review with both sides'
  evidence and the first decider. Start mediation, uphold or reject with an outcome message both sides see, internal
  notes and a reason; resolving asks for the irreversible tick. For a business objection the outcomes read as what
  they do ("Publish the review (the objection is not accepted)" / "Accept the objection (the review is rejected)").
  Whoever raised the dispute or made the decision under dispute is refused by the server and the screen says a
  colleague must decide.
- Open cases and disputes are readable only while they are open and unassigned or the caller's (the backend's purpose
  check); decided ones show the summary from the list.
- Review cases run on the moderation case workspace of AC8 (same reading, actions, history and closing).

## Moderation (AC8)

- **Content** (`/content`), tabs by role. **Reports** (moderators, support): user reports by status, target type and
  reason, safety reasons first, with the Docs/23 §6 timer (4 h for unsafe advice, media without consent and private
  data; 24 h reviews; 48 h the rest). A report is triaged with a reason: **Open a case** (severity chosen; the three
  safety reasons start at high and cannot go lower), **Add to that case** when an open case about the same item
  exists (moderators), or **Dismiss**. Opening a case gathers every open report about the same item.
  **Content**, **Accounts & organizations** and **AI output** (moderators, platform admins): case queues of
  `admin.cases_list`. A queue of several types reads every type at once (up to 50 each, `?type=` pages one type on
  the server); safety cases sort first, then severity, then age; the Content queue has the Docs/23 views (reported,
  AI flagged, held by a rule, unsafe advice, consent and privacy), which narrow the loaded cases.
- **Inventory** (`/inventory`): cases of listings and fitment records.
- A case opens for its purpose (`?case=<id>&purpose=case:<id>`): the item as the public sees it (text, state,
  owner, "Open the public page" for published posts, open questions and active shops), a file inline with a
  "CarPal internal" watermark and no download button (`admin.media_download_url`, display copy), the case facts,
  the AI risk and the action history. **Take this case** assigns it to you. The actions are the ones that fit the
  item in its state (the backend's moderation targets): approve held content, hide, remove, restore, request changes
  (showcase items, listings), reject a fitment record; a showcase item cannot be approved without a valid customer
  consent. Accounts: warn, **Suspend** (asks for the security key again; no end date until timed suspensions are
  lifted automatically, BR-07), reactivate. Organizations: a **trust penalty** (1-100 points, 12 months, security key,
  second confirmation) and **Badges** (approve the Verified Business badge, revoke a badge; the badge id is entered,
  because no read lists an organization's badges yet, BR-31). Every action needs a reason; the case is closed with an
  outcome and a resolution. Merging duplicates is not offered until BR-08.

## Integration tests

`pnpm test:int` signs a fresh ADM account in through the BFF (password, emailed code, a software security key, then
the key at aal3) and calls the forwarder. It needs backend `pnpm dev` with these settings (environment or
`backend/.env`; see `backend/.env.example`):

```
CARPAL_OAUTH_REDIRECT_URIS={…, "cp-web-admin":["https://localhost:3200/bff/oauth/callback","https://localhost:3300/bff/oauth/callback"]}
CARPAL_WEBAUTHN_RP_ID=localhost
CARPAL_WEBAUTHN_ORIGINS=["https://localhost:3000","http://localhost:3200","http://localhost:3300"]
CARPAL_RATE_LIMIT_SCALE=100
```

Strict mode (the acceptance run): make the key files with `node backend/deploy/gen-client-keys.mjs >pwa-keys.json`
and `node backend/deploy/gen-client-keys.mjs --admin >admin-keys.json`; start the backend with `CARPAL_STRICT_AUTH=1`
and `CARPAL_OAUTH_CLIENT_JWKS` set to the output of `gen-client-keys.mjs --public pwa-keys.json admin-keys.json`; then
run `pnpm test:int` with `CARPAL_STRICT_AUTH=1` and `CARPAL_ADMIN_CLIENT_PRIVATE_JWKS` set to the content of
`admin-keys.json`. The test creates its account with backend `pnpm dev:staff create` (dev only), or uses
`CARPAL_INT_STAFF_EMAIL` (password `admin-console-int-password`, no passkey yet).

## End-to-end tests

`pnpm e2e` builds and runs Playwright on :3300. `tests/e2e/smoke.spec.ts` and `bff.spec.ts` need no backend.
`tests/e2e/signin.spec.ts` (AC4), `approvals.spec.ts` (AC5: the four-eyes round trip with two ADM accounts; it
re-files a data retention policy with its own values, so approving it changes nothing) and `settings.spec.ts` (AC6:
the rate reaches config.client, the kill switch on and off with a second admin, a stale flag version, plans,
retention and an assignment, Persian), `reviews.spec.ts` (AC7: a reviewer confirms a Path 2 review end to end, a
moderator cannot decide, a business objection decided by a different staff member, Persian) and `moderation.spec.ts`
(AC8: a reported post triaged, hidden, restored and closed; a suspension that asks for the security key, Persian) sign
real staff in. `moderation.spec.ts` turns the community flags on in dev (backend `pnpm dev:flags set community on`)
and has a shop publish a post and a customer report it; the backend asks for the key only when the sign-in is older
than 10 minutes, so the spec answers the first suspend call with the backend's `STEP_UP_REQUIRED` and the replay
after the key goes to the real backend.
`reviews.spec.ts` creates its shop, customers and Path 2 reviews through the API as cp-mobile users
(`tests/e2e/app-user.ts`: sign-up, the mailed link, the code flow with PKCE and DPoP, a proof of work whenever the
server asks for an attestation; it needs no client key, and needs `https://carpals.ir/oauth/callback` among the
cp-mobile redirect URIs, the dev default). `settings.spec.ts` reads config.client on the api host
(`:8080`) as an anonymous app (`tests/e2e/public-api.ts`), puts the rate and the flags back, and has a second admin
reject the plan and retention changes it files. They need
backend `pnpm dev` with the settings above (the `:3300` redirect URI and WebAuthn origin), create one account per test
with backend `pnpm dev:staff create` (dev only; `e2e-…@staff.carpals.test` accounts stay in the dev database), read the
emailed code from `backend/.data/outbox-mail.jsonl`, and use Chrome's virtual authenticator as a device-bound
security key. For the strict run, export `CARPAL_STRICT_AUTH=1` and `CARPAL_ADMIN_CLIENT_PRIVATE_JWKS` before
`pnpm e2e`; the Playwright config passes them, and the dev redirect URI, to `next start`. The idle test mocks the
browser clock.

## Language and theme

No locale segment in URLs. The language comes from the `cpa_locale` cookie, then Accept-Language, then
`CARPAL_ADMIN_DEFAULT_LOCALE` (fa). From AC4 on, the signed-in staff member's `me.locale` decides. Themes: Daylight,
Sunlight (high contrast) and Night (`cpa_theme` cookie; automatic when unset). The cookie names differ from the
PWA's because cookies on localhost are shared across ports.

## Rules

- No widening: the BFF forwards only the operations in `src/lib/api/generated/operations.ts`.
- No personal data in the browser: no Web Storage or IndexedDB for responses (lint-enforced), no service worker, no
  analytics; every page answers `Cache-Control: private, no-store` and `X-Robots-Tag: noindex`.
- Logical CSS properties only; colours and sizes from the design-system tokens.
